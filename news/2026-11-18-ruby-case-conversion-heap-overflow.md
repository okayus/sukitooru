## 要点

Ruby の処理系にあった、メモリの安全（第26章 場面6）を壊す脆弱性の話である。1 バイトの符号化で ß（1 バイト）を大文字にすると SS（2 バイト）になるが、変換のループは 1 バイト分の空きしか確かめず、結果を入れる区画の直後に 1 バイトを書く。Veria Labs は、Rails と Sinatra の既定の設定のまま認証の前にこの欠陥まで届くと書き、勧告は、条件によってはリモートからコードを実行できる PoC があると書く。Ruby は 2026-11-18 の 4.0.10・3.4.13・3.3.14 で直した。

## どの層の話か <!-- tab: 層 -->

種類は事故（脆弱性の公表と修正）で、働くのは実行時である。Ruby のプログラムが、1 バイトの符号化の文字列の大文字・小文字を変えるときに起きる。

| 層 | このニュースで起きること | 章・場面 |
|---|---|---|
| Web アプリの枠組み | Rails と、classic 形式の Sinatra は、既定の設定のまま認証の前にこの変換まで届く。ほかの枠組みと素の Rack は、既定では届かない（Veria Labs）。どの欄から届くかは公開されていない | 教材に無い（Web アプリの枠組み）。近いのは [22章 場面5][22-5] |
| 文字の符号化 | Ruby の文字列は符号化の名前を持ち、大文字・小文字の変換の関数も符号化ごとに別にある。当たるのは ISO-8859 と Windows-125x の 1 バイトの符号化で、UTF-8 の文字列は別の関数を通り、当たらない | [10章 場面2][10-2]、[26章 場面1][26-1] |
| 大文字・小文字の変換 | 1 バイトの符号化の多くには大文字の ß が無く、ß を大文字にすると SS の 2 文字になる | [32章 場面3][32-3] |
| **メモリの安全** | 長さを確かめるのは C のコードの役目で、確かめ方が 1 バイト足りなかった。ß を 21 個並べると、区画の外へ 1 バイト書き、1 バイト読む | [26章 場面6][26-6] |

## 何が起きたか <!-- tab: 動き -->

ß を 21 個並べた ISO-8859-1 の文字列を大文字にすると、結果は 42 バイトになるが、区画は 41 バイトしかない。最後の S が区画の外に書かれ、結果を写し出すときにもその 1 バイトを読む。

## 中身 <!-- tab: 中身 -->

### 起きたこと

- 2026-11-18、Ruby は 4.0.10・3.4.13・3.3.14 を出し、脆弱性 7 件を直した。大文字・小文字の変換が 2 件（この欠陥と、整数のあふれからヒープがあふれる GHSA-87fm-7w84-j2px）、正規表現が 5 件である。CVE の番号は申請中で、勧告は GHSA の番号で呼ぶ。
- この欠陥を見つけたのは、勧告の謝辞では Stephan Lipp（Ada Logics）と Anthropic である。
- Veria Labs は深刻度を Critical とし、PoC は利用者が上げる時間をおいて 1 週間後に出すと書く。
- Veria Labs の表（2026-11-19 19:59 UTC の時点）では、GitLab 19.6.0（同梱の Ruby は 3.3.13）、GitHub Enterprise Server 3.22.5（4.0.9）、Chatwoot 4.20.0（3.4.4）が当たる。Mastodon 4.7.6・OpenProject 17.9.8・Discourse の基本のイメージは 4.0.10 を同梱して直っている。

### 原因

- 14 個の変換の関数で、1 文字に 2 バイトを書くのは ß の所だけだった。
- UTF-8 などの Unicode の変換の関数は、区画の終わりの 12 バイト手前で止まる（`CASE_MAPPING_SLACK`）。1 バイトの符号化の関数には、この余りが無かった。区画に足す 20 バイトには「1 文字が長くなる分は 16 で足りる」という注釈が付いている。
- 変換の関数を呼ぶのは `upcase`・`swapcase`・`downcase(:fold)`・`casecmp?`。ふつうの `downcase` は ß を変えないので、長くならない。Veria Labs によれば、このループは 2.4.0 からある。
- 書く 1 バイトは、大文字にするときは `S`（0x53）、畳み込み（`downcase(:fold)`）のときは `s`（0x73）である（Veria Labs）。

### 対策

- 4.0.10・3.4.13・3.3.14 以降に上げる。3.3 はセキュリティの修正だけを出す段階にあり、3.2 以前は保守が終わっていて直った版は出ない（勧告）。
- Ruby を同梱するソフトウェアは、作る側の直った版を入れる（Veria Labs）。勧告に回避策は書かれていない。
- Veria Labs は、既定で届かない枠組みでも、古い符号化で受け取った文字列を大文字にするアプリのコードは当たりうると書く。

### 出典と確かさ

- Ruby の[セキュリティ勧告](https://www.ruby-lang.org/en/news/2026/11/18/multiple-vulnerabilities-in-regexp-and-string/)（mame、2026-11-18）と [4.0.10 の告知](https://www.ruby-lang.org/en/news/2026/11/18/ruby-4-0-10-released/)（同じ日。3.4.13・3.3.14 も）。7 件の一覧、当たる版、謝辞、PoC があることはここから取った。
- Veria Labs の [ruby2ßhell](https://verialabs.com/ruby2shell/)（2026-11-19 19:59 UTC に更新。最初に出た日はページに無い）。区画の大きさ、21 個の ß、0x53 と 0x73、読み過ぎ、枠組みと同梱のソフトウェアの表はここから取った。
- 確かめたこと: cache.ruby-lang.org の ruby-4.0.9.tar.xz と ruby-4.0.10.tar.xz（SHA-256 は告知と一致）を tar（GNU tar 1.35）で展開し、`enc/` と `string.c` を diff（GNU diffutils 3.10）で比べた。ビルドも実行もしていない。区画の大きさの式、注釈、`SHARP_s` が 0xdf であること、Unicode の側の 12 バイト、直した 14 個のファイルは、このソースで読んだ。手元にあった Ruby 3.3.6 で、ß を 1 つだけ含む文字列のバイト数を ISO-8859-1・Windows-1252・UTF-8 で変換の前後に比べ、0xDF を ISO-8859-5 で読んだ（あふれは起こしていない）。
- 出典どうしの食い違い: 勧告の投稿の日は 2026-11-18、履歴の欄は 2026-11-19 00:00:00 (UTC)。勧告は当たる版の下限を書かず（3.3.13 以前）、Veria Labs は 2.4.0 からと書く。
- 確かめていないこと: Rails と Sinatra で、要求のどこからこの変換に届くか（Veria Labs は書いていない）。コードを実行できることは、勧告と Veria Labs の説明だけによる。GitHub の勧告と修正のコミット（ruby/ruby@d582f8f）は、この実行の環境からは開けなかった（403）。3.4.13 と 3.3.14 のソースと、ほかの 6 件は読んでいない。
