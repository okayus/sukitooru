### 段階（dir: 'rx'、既定）

| 段階 | 題 | 図の決まった姿（止めたとき） |
|---|---|---|
| 1 | ドライバが空きバッファを並べ、RDT を書く | 0〜6 番に番地 0x1000〜0x4000（0x800 ずつ）、7 番は空けておく。RDH = 0、RDT = 7。NIC の控えは 0〜6 番の 7 個 |
| 2 | DMA エンジンが 256 B ずつ書く | バッファの帯に 256・256・256・256・256・234。DMA エンジンは 0x15EA・0 B・6 / 6 回。0 番の DD はまだ 0 |
| 3 | 完了の印を書き戻し、割り込みは 1 回 | 0〜2 番に長さ 1514・DD 1、RDH = 3。MSI-X は「止めた（自動）」、割り込みコントローラを強調 |
| 4 | ハンドラが poll を予約し、poll が取り出す | 7・0・1 番に新しいバッファ（0x4800・0x5000・0x5800）、2 番を空けておく、RDT = 2。sk_buff は data = 先頭 + 0、len 1,514 |
| 5 | data を進めて層を上がる | data = 先頭 + 62、len 1,452。3 つのヘッダは外した姿（破線） |
| 6 | 受信キューにつなぎ、待つタスクを起こす | 受信キューに 1452 が 3 個、PID 4133 は R 実行可能 |

### 段階（dir: 'read'）

| 段階 | 題 | 図の決まった姿（止めたとき） |
|---|---|---|
| 1 | ヘッダを前に書き、送信リングに載せる | 送信ディスクリプタ 0 番に 0x6000・1312・DD 0。TDH = 0、TDT = 1。sk_buff は data = 先頭 + 0、len 1,312 |
| 2 | NIC がディスクリプタを読む | NIC の控えに「0 番：0x6000・1,312 B」 |
| 3 | フレームを 512 B ずつ読み出す | 帯に 512・512・288。DMA エンジンは 0x6520・0 B・3 / 3 回。送信 FIFO が満ちる |
| 4 | MAC が FCS を足して送り出す | FIFO が空になる（動いている間は回線の線が e の色） |
| 5 | 完了の印を書き戻し、割り込む | 0 番に DD 1、TDH = TDT = 1。MSI-X は「止めた（自動）」 |
| 6 | poll が使い終えたバッファを返す | 0 番は空き、バッファは解放した色、sk_buff は消える |

## 模式にした所

- リングは 8 個（igc の既定は 256 個）。番地（0x1000〜、0x6000）は例で、物理アドレスとして書いた。IOMMU（第7章 場面4 段階5）は省いた。
- バッファの帯は 2 KiB を 286 px にした比例の帯。ヘッダの 62 B は細すぎるので、先頭 62 B だけを拡大して描き、data の位置は「先頭 + n」で書いた。sk_buff の head と前の余白（headroom）は描いていない。
- 書き込みの 1 回 256 B は例（I210 が持てる Max Payload Size は 128・256・512 B で、実際の値は OS とファームウェアが決める）。第7章 場面4 の図の札は 128 B。
- 2・3 個めのフレームの DMA は描かず、ディスクリプタの書き戻しだけにした。
- DMA エンジンの中の「番地」「残り」「回数」は、出す要求の番地と残りの量を示す模式（I210 のデータシートは DMA エンジンの中の作りを書いていない）。
- NIC とメモリの間の道を直結で描いた（実物は CPU の中のルートコンプレックスを通る。図の説明に書いた）。
- ディスクリプタの先読みは 1 回の要求で 7 個（112 B）。I210 は受信で 1 回 16 個まで読む。
- 完了の判定: データシートと e1000e は DD を見る。igc は書き戻した長さ（0 でない）で判定する。図と文はデータシートの DD に合わせた。
- sk_buff を作る時: igc は poll でページのバッファを build_skb で包む。e1000e は先に作った sk_buff のデータ領域をバッファにする。図は poll で sk_buff にする igc の形。
- GRO（napi_gro_receive）、2026-11 の master の UDP が受信キューの前に通す NUMA ノードごとの列、ソフト割り込みの全体の予算（netdev_budget）は省いた。
- 送信のヘッダ: 実装は UDP・IPv6 のヘッダの場所を写すときに確保し、Ethernet は skb_push で前に足す。図は 3 つを順に前へ書く形にし、data の移り方は len の変わり方に合わせた。
- 割り込みの束ね: igc は間隔を動的に変える（約 14〜250 µs）。図の「束ねる間隔」はその待ち。
- 送信の割り込みもベクタ 34 にした。igc が受信と送信の組で 1 本のベクタを使うのは、受信キューの数（CPU の数と上限 4 の小さい方）が上限の半分を超えるとき、つまり CPU が 3 個以上のとき。

## 迷った所と決め方

- **読む向きは params にした（1 段階にまとめない）。** 読む向きは要求と完了の往復（non-posted）で、書く向き（posted）と仕組みが違う。受信の 6 段階のどれかを削って 1 段階にすると、1,452 B の道（第9章 場面2・3・5・6 の行き先）が途切れる。送信の 6 段階にすると、第9章 場面6 段階5 の sendto 1,250 B・送信リング・送信の完了の割り込みと値がそろい、第8章 場面3・6 の「装置がメモリを読む」の行き先にもなる。params の名前は指示どおり `dir: 'read'`。
- **title は「NIC の受信と送信」。** title は params で変えられない（板の道筋に出る）。第8章の読む向きの印から開いても食い違わない名前にした。
- **リングは 8 個（第9章 場面6）。** 第7章 場面4 は 3 個で、RDT = 3 は Intel の決まり（番号は 0〜個数−1 を回り、head = tail は空）では成り立たない（下の「章で直したほうがよい所」4）。使う所の多い第9章に合わせ、束ねる数は第7章 場面4 と第9章 場面3 の受信キューに合わせて 3 個にした。
- **NIC の例は Intel I210・I225（igb・igc）。** 第9章 場面6 の補助の図が igc を挙げ、I225/I226 は家庭の PC の板にも載る 2.5GbE の NIC。I210 のデータシートが受信・送信の流れと PCIe の要求を 1 冊で書いている。e1000e（I219 など）は RDT の位置（0x2818）と sk_buff の作り方が違うので、記録にだけ書いた。
- **書き込みの大きさは 256 B。** 第7章 場面4 の「128〜512 B」の中で、6 回に分かれて図で数えられる大きさ。第7章 場面4 の図の札（128 B）とは違うので、図の説明に「1 回の大きさは例」と書いた。
- **割り込みを止めるのは誰か。** napi.rst は「ハンドラが止めてから予約する」形を書き、igc・e1000e の MSI-X では NIC が自動で止める（EIAM）。文は「割り込みを止めたまま予約する」にし、図の MSI-X の札を「止めた（自動）」にした。
- **送信の DD は「読み終えた」の印。** I210 は、データの完了が揃った時点でディスクリプタを書き戻す（電線に出し終えた時ではない）。段階5 にそう書き、題を「使い終えたバッファを返す」にした。
- **部品の中の印の行き先。** 受信リングは指示の候補の 07 s4.2 ではなく 27 s5.2（リングバッファ）にした。07 s4.2 は部品の元の章で、部品が同じことを細かく見せた後に開いても先へ進まない。待つタスクを起こす → 09 s5.5 は指示どおり（部品より上の os の層だが、起床の仕組みはそこにしか無い）。割り込み → irq-entry はまだ無いので 07 s3.4 にし、表の最後の行に書いた。
- **「止めたときの姿」は、各段階の最後の場面（決まった姿）。** 動きの中の場面（ph）は U.seq で段階に入ってからの時刻だけから決め、文字と色は値が変わったときだけ書き換える（時刻が飛んでも書き換えを落とさない）。

## 章で直したほうがよい所

1. **chapters/09-os.html 場面6（IPv4 の値が残っている）**: fd 23 は `socket(AF_INET6, SOCK_DGRAM)` で、受け取る 1,452 B は 1,500 − 40 − 8（IPv6）だが、図の層「IP」の説明が「IP ヘッダ 20 B を外す」、段階3 の補助の図が「さらに 20 で IP、8 で UDP」、sk_buff の図の区切りも IPv4 の幅。印のつなぎの一文「0x0800 なら中身を IP の処理へ渡す」（→ 13-ethernet.html#s3.4）は IPv6 なら 0x86DD。印「IP のプロトコル番号」（→ 18-ip.html#s1.4、IPv4 ヘッダの欄）は、IPv6 なら「次ヘッダ 17」で行き先は 18-ip.html#s3.5。段階3 の本文「プロトコル番号（17=UDP、6=TCP）」も IPv6 では次ヘッダ。直すと、部品の段階5 と値がそろう。
2. **chapters/09-os.html 場面6 段階4 の frame**: `st.procCall` の最後の文字が「戻り値 1350 → QUIC の復号へ」のまま（1372 行あたり）。P4 で受け取る量を 1,452 B にしたときの直し残し。
3. **chapters/09-os.html 場面6 段階2 の図**: 札「割り込み線（IRQ）」。PCIe の NIC は線でなく MSI-X（決まった番地への書き込み）で割り込む（第7章 場面3 段階2 もそう書く）。「割り込み（MSI-X）」などにする。
4. **chapters/07-shuuhen.html 場面4 段階2〜4**: (a) ディスクリプタ 3 個のリングで RDT = 3。Intel の RDT は渡した最後の次の番号で 0〜(個数−1) を回り、head = tail は空なので、3 個のリングで渡せるのは 2 個まで（RDT = 3 は範囲の外）。リングを 4 個にして RDT = 3 にするなど。(b) addr 0x1000・0x1200・0x1400 に len 1514。間隔 0x200 = 512 B に 1,514 B のバッファは重なる。2 KiB 間隔（0x1000・0x1800・0x2000）にし、IOMMU の許可（0x1000〜0x16FF）も合わせる。(c) 急がない: Intel の NIC では、ドライバが書くのは番地だけで、長さ（受け取った長さ）は NIC が書き戻す（バッファの大きさはキューごとの設定）。本文の「先頭アドレスと長さを書いたディスクリプタ」は装置によっては正しい（virtio など）ので、変えるなら「先頭アドレス（装置によっては長さも）」。
5. **chapters/07-shuuhen.html 場面2（急がない）**: TDT の位置が「+0x18」。CTRL +0x00・STATUS +0x08 は Intel の NIC と同じだが、TDT は e1000e で 0x3818、I210・I225 で 0xE018。模式なら図の説明か補足に「位置は例」と書く。

- リング: RDT・TDT は「処理してよい最後の次」（7.1.4.5・7.2.2）。RDT と RDH の差が NIC の使える数で、追いつけば 0 個（7.1.4.5.1）。RDLEN は 128 B の倍数なので、リングは 8 個の倍数で、8 個は I210 で組める最小。igc_desc_unused（ntc > ntu なら 0、そうでなければ count に ntc − ntu − 1 を足す）で 1 個は空く。RDT = 7 → 2 の計算を確かめた。
- レジスタの位置: RDH 0xC010・RDT 0xC018・TDH 0xE010・TDT 0xE018（8.10.7・8.10.8・8.12.13・8.12.14、igc_regs.h の IGC_RDH(n) など）。第7章 場面2 の 0xFEB0_0000〜0xFEB1_FFFF（128 KiB）の中に入る。
- PCIe: 書き込みは posted で MAX_PAYLOAD_SIZE 以下（I210 が持てるのは Flash で決まる 128・256・512 B、Device Control の既定は 000b = 128 B）。読み出しは min(2 KB, Max_Read_Request_Size)（既定 010b = 512 B）で、4 KB をまたがない（3.1.4.2）。記述子の書き戻しと MSI・MSI-X の書き込みは relaxed ordering にしない（3.1.4.5.2）。msi-howto.rst「割り込みを起こす書き込みはデータの書き込みを追い越さない」。
- 束ね: EITR は前の割り込みから決めた間隔の間は割り込まない（7.3.5）。igc の ITR 980・196・56 は 0.25 µs 単位で約 245・49・14 µs（札の「約 14〜250 µs」）。
- 受信ディスクリプタ: 読む形はバッファの番地（と見出し用の番地）だけで、長さ PKT_LEN と DD は NIC が書き戻す形に書く（7.1.4.2）。
- Linux（master、2026-11-18）: igc_msix_ring は ITR を書いて napi_schedule_irqoff だけ、EIAM で NIC が割り込みを自動で止める、igc_poll は送信の後始末 → igc_clean_rx_irq → napi_complete_done → igc_ring_irq_enable、igc_clean_rx_irq は書き戻した長さを見て build_skb し最後に igc_alloc_rx_buffers で tail を書く、igc_clean_tx_irq は DD を見て napi_consume_skb（予算は tx.work_limit = 128 で受信の 64 と別）、netif_napi_add → NAPI_POLL_WEIGHT 64、napi.rst（7.4.0-rc3。Rx だけを budget で数え、Tx は budget と関係なく処理、割り込みは napi_complete_done の後に戻す、poll は普通ソフト割り込み）、eth_type_trans → skb_pull_inline(ETH_HLEN)、ip6_input.c（transport_header = network_header + 40、pskb_pull、inet6_protos[nexthdr]）、udp_csum_pull_header（8 B）、__udp_enqueue_schedule_skb（NUMA ノードごとの列から sk_receive_queue の末尾へ、sk_data_ready）、sock_def_readable（wake_up_interruptible_sync_poll）、asm/msi.h（0xfee00000、データの下位 8 ビットがベクタ）、igc の受信・送信の組（rss_queues = min(4, CPU の数) が 2 を超えるとき）。
- 値: 計算を全部やり直した（256 × 5 + 234 = 1,514、0x1000 + 1,514 = 0x15EA、2・3 個めの終わり 0x1DEA・0x25EA、7 × 16 = 112 B、14 + 40 + 8 + 1,452 = 1,514、512 × 2 + 288 = 1,312、0x6000 + 1,312 = 0x6520、1,312 + 4 = 1,316、1,250 → 1,258 → 1,298 → 1,312、リフィル 3 個で RDT = (7 + 3) mod 8 = 2）。上の章の値（fd 23・PID 4133・UDP 51234・epoll_wait(5, …)・recvfrom(23, buf, 65536, …)・sendto(23, buf, 1250)・受信リング 8 個・ベクタ 34・0xFEB0_0000）と一致する。
