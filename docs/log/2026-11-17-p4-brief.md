## 言葉の定義

- **下の層の仕組みに頼っている所**: 段階の文や図が、ある仕組みの結果を使っていて、その仕組み自体はその場面で説明していない所。例: 第9章 場面3 段階2「CPU がモードを切り替える」は CPU の中の仕組みに頼る。第9章 場面3 段階3 の受信キューのデータは、NIC が DMA で書いたもの（第7章 場面4）に頼る。名前が出てくるだけの所、その場面の中で説明し終えている所、一般的な背景は数えない。
- **行き先**: その仕組みを説明している場面・段階（`07-shuuhen.html#s4.3`）。どの章でもよい（第26〜36章も、同じ章の別の場面も、下の層の場面ならよい）。一番深い所ではなく、**すぐ下の層**を選ぶ。その先は、行き先の場面の印でさらに掘れる（いま無くても P4 の他の担当が張る）。
- **状態**（どれか 1 つ）:
  - **有る**: 行き先の段階がその仕組みを説明していて、例（値・物）が上の段階と合うか、例によらない説明。
  - **例が違う**: 行き先の段階がその仕組みを説明しているが、例の値や物が上の段階と違う（上は 1,452 バイトの TCP の断片、下は 64 バイトのフレーム、など）。印を張る。P5 で、上の値で動く部品に置き換える候補になる。
  - **無い**: 教材のどこにもその仕組みの説明が無い。または、一番近い段階が上と同じ抽象で止まる（第9章 場面3 段階2「CPU がモードを切り替える」→ 第7章 場面3 段階4「同時にカーネルモードに切り替わる」は、どちらも切り替わる仕組みを説明しない）。印は張らない。何が足りないか（部品にするなら何を見せるか）を書く。P5 の部品の候補になる。

## 印の書き方

authoring.md §5.5 の仕様に加えて、P4 では次を守る。

```js
// 場面の setup の中、印を付ける要素を作った後に、1 行に 1 つ
YT.drill.mark(st.hwBand, { to: '07-shuuhen.html#s4.3', label: 'NIC → DMA', at: [404, 492], steps: [3], bridge: '受信キューのデータは、NIC が CPU を使わずにメモリへ書いたもの（DMA）' });
```

- **形**: 場面の `const sK = { … setup(ctx) { … } }` の中に書く。1 行に 1 つ。第 1 引数はカンマを含まない式（`st.box` など。要素を変数に持っていなければ、作るところで `st.xxx = S.rect(…)` のように持たせる）。第 2 引数は文字と数の値だけの対象（変数・式・テンプレート文字列を使わない）。道具（drillcheck・lencheck・xrefcheck）は印をこの 1 行の形で読む。ループや関数の中で印を作らない。
- **steps**: 1 始まり（URL の `#s3.2` と同じ）。段階の文か図がその仕組みに頼っていて、要素が見えている段階だけ。
- **1 つの段階に出る印は 3 つまで**。説明欄の下の一覧が 2 行を超えると、1画面版の左の列の高さを食う（drillcheck が 4 つ以上を注意に出す）。
- **at は必ず書く**（札の中心。場面の svg の viewBox `0 0 960 560` の座標。`<g transform>` の中の要素でも、図全体の座標で書く）。札は 26×22px。要素の近く（どの要素の印か迷わない位置）で、文字・ほかの札・矢印の先・動く札の止まる位置に重ねない。`--overlap` が「掘り下げの印の札が「…」を隠す」「札どうしが重なる」を出す。
- **bridge（つなぎの一文）**: 60 字まで。上の段階の語で始めて、下の場面の語で終える。下の場面の説明を繰り返さない。下の場面の例の値と食い違う値を書かない。比喩を使わない（authoring.md §8）。
- **label**: 上の要素の名前。20 字まで。
- **to**: 行き先の段階の本文を読んで、仕組みを説明している段階を選ぶ（場面の段階1 とは限らない）。迷ったら行き先を写真で見る（`timeout 300 node tools/shot.mjs chapters/NN-*.html --scene K --step J --at 2 --out <一時置き場>/at`）。
- **部品**: 既存の部品 `cpu-mode` が合う所だけ `part: 'cpu-mode', step: N` で使ってよい。P4 では部品を新しく作らない。
- **変えないもの**: 段階の文・段階の数・場面の構成・図。変えてよいのは、印を付けるために要素を変数に持たせる所だけ。本文の誤りを見つけたら、直さずに記録の「他の章で直したほうがよい所」に書く（受け持ちの章でも同じ）。
- `YT.zoom` の板（第5章 場面4、第6章 場面1・3）が開いている間、元の図の札は出ない。印は元の図の要素に付ける。
- 本文の中の他の章へのリンク（`[[13-ethernet.html#s4.2|…]]`）は、印の候補を探す手がかりになる。印とリンクは両方あってよい。

## 検証（完了の条件）

章ごとに次を通す。

1. `node tools/drillcheck.mjs --list chapters/NN-*.html` — 「印の無い場面」と「注意」が無い。向きが「横」の印は、表の判断に理由を書く（層の登録簿の down は粗いので、正しい依存でも「横」になることがある）。
2. `node tools/xrefcheck.mjs chapters/NN-*.html` — 問題 0 件。
3. `node tools/lencheck.mjs chapters/NN-*.html` — 印の行（つなぎの一文・上の要素の名前）の超過が無い。前からある本文の超過は直さず、報告に書く。
4. `timeout 900 node tools/verify.mjs --nav --overlap --drill chapters/NN-*.html` — ✓。文字の重なりの注意が増えていない（前からあるのは第1章 場面1 段階4 の乱数と第2章 場面6 の 9 件だけ）。掘り下げの行が「印 N 個を開いた」で、✗ が無い。
5. 写真: `timeout 900 node tools/verify.mjs --shots <一時置き場>/shots --all-steps chapters/NN-*.html` で、**印のある段階の写真を全部** Read ツールで見る。札がどの要素の印か分かる位置か、文字・線・札に重なっていないか。`--drill --shots` で開いた板も、1920 幅と縦読み版（`-phone`）を数枚見る。
6. `--dark` を付けて 2〜3 枚。

## 守ること

- 変えてよいのは、受け持つ章のファイルと、自分の記録のファイルだけ。assets/・tools/・index.html・ほかの章・ほかの docs は変えない（直したほうがよい所は報告に書く）。
- ほかの担当が同時にほかの章に印を張っている。`--drill` で開いたほかの章の埋め込みに、その章の JS のエラーやはみ出しが出たら、少し待って走らせ直す。ほかの章は直さない。
- tools/serve.sh は使わない。verify.mjs・shot.mjs は必ず `timeout 900`（shot は 300）を付けて走らせる。Chrome のプロセスを名前で止めない（pkill・killall を使わない）。
- 写真と一時ファイルは一時置き場にだけ置く。プロジェクトの中に置かない。一時置き場は消えることがあるので、記録はプロジェクトの記録のファイルに書く。
- サブエージェントを呼ばない。git の commit・push をしない（調整役がする）。
- 事実の確認が要るときは WebSearch / WebFetch（ToolSearch で読み込む）を使ってよい。つなぎの一文は、上と下の場面に書いてあることの範囲で書けば、新しい事実は要らない。
