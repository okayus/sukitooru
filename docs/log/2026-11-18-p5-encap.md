# 作業記録 2026-11-18（P5 部品 encap）

[layers-plan.md](../layers-plan.md) §3 P5「部品を足す」の部品 encap（カプセル化）。指示は [2026-11-18-p5-brief.md](2026-11-18-p5-brief.md)。

## 作ったもの

| ファイル | 中身 |
|---|---|
| assets/parts/encap.js | 部品「カプセル化」。視聴ページの要求（GET /watch）に、外側へヘッダが付いてビット列になるまでを、行ごとの層・足したバイト数・欄の値で見せる。6 段階。params で TCP＋TLS（既定）・QUIC・GRE（第22章の Maglev）を切り替える |

layer は `link`（使う所の層 player・browser・ip・transport・tls・http・delivery・os のどれからも down で届く）、home は `11-sou.html#s3`。

## 設計

図は 1 行が 1 つの層（上から 6 行）。行ごとに、上の行の中身を変えずにヘッダ（その段階で足したものは x の枠）を外側へ足す。右端に行の合計と足したバイト数、下の欄にその段階で足したヘッダの欄・値・16 進を出す（接続ごとに変わる欄は 16 進を空けて中身を書く）。TCP＋TLS と QUIC では、行 2 と行 3 の間に「↑ ブラウザの中 ↓ OS（カーネル）の中」の境目を引く。

### 段階の表

| 段階 | via: 'tcp'（既定） | via: 'quic' | gre: 1（段階1〜4 は via のまま） |
|---|---|---|---|
| 1 | HTTP/2：HEADERS フレーム（見出し 9 B ＋ HPACK 450 B ＝ 459 B） | HTTP/3：HEADERS フレーム（見出し 3 B ＋ QPACK 450 B ＝ 453 B） | ← |
| 2 | TLS 1.3：見出し 5 B・種別 1 B・タグ 16 B を足す → 481 B | QUIC：見出し 10 B・STREAM フレーム 2 B・タグ 16 B を足す → 481 B | ← |
| 3 | TCP 20 B → 501 B | UDP 8 B → 489 B | ← |
| 4 | IPv4 20 B → 521 B（プロトコル 6） | IPv4 20 B → 509 B（プロトコル 17） | ← |
| 5 | Ethernet 14 B ＋ FCS 4 B → 539 B | → 527 B | Maglev 2 が GRE 4 B と外側の IPv4 20 B を足す → 545 B（QUIC は 533 B） |
| 6 | プリアンブル 7 B ＋ SFD 1 B → 547 B ＝ 4,376 ビット、送る順のビット | → 535 B ＝ 4,280 ビット | GFE 2 が外側の 24 B を外して受け取る → 521 B（509 B）。応答は DSR |

動き: 段階6（ビット列）に、送っている所を示す x の線（5 秒で端から端。進む速さはバイト数に比例）。止めているときは、プリアンブルと SFD を送り終えた所に置く。GRE の段階6 は、外した外側の IP と GRE が持ち上がって消える（止めているときは破線の枠で残す）。ほかの段階は止まった図。

### params

| params | 既定 | 中身 |
|---|---|---|
| via | 'tcp' | 'quic' で同じ要求を HTTP/3 → QUIC → UDP で送る姿 |

例が章どうしで合わない所と、どれを使ったか:

- **要求の大きさ: 第21章の 459 B（HTTP/2）を使い、第11章の 300 B は使わない。** 第11章 場面3 の 300 B は「ここでは 300 バイトとする」と置いた HTTP/1.1 の要求文で、TLS も省いている（補足に断りがある）。視聴ページの HTML は HTTP/2 で取る（plan.md の実測、第21章、第25章 場面2 段階5）ので、第21章 場面3 の HEADERS（450 B ＋ 9 B）を使った。第11章との差（300 → 459、TLS の 22 B）は、第11章からの印のつなぎの一文で言う（「全長は 340 でなく 521」「フレームは 358 B でなく 539 B」）。
- **QUIC の姿: 「動画の断片の POST」ではなく、www.youtube.com への同じ GET /watch を HTTP/3 で送る姿にした。** 理由は「迷った所」の 2。
- **QPACK の大きさ 450 B は例。** HTTP/3 の要求のヘッダを縮めた大きさは教材に無いので、HTTP/2 の HPACK と同じとした（図・注記・段階1 の文に「例」「同じとした」と書いた）。

## 計算で決めた値（node で計算し直した）

```
TCP＋TLS: 450 + 9 = 459 / 459 + 1 + 16 = 476 = 0x01DC（レコードの長さの欄） / + 5 = 481 / + 20 = 501 / + 20 = 521 = 0x0209（IP の全長）
          / + 14 + 4 = 539 / + 8 = 547 / 547 × 8 = 4,376 ビット / 1 Gbps で 4.376 µs → 4.4 µs
QUIC:     長さ 450 の可変長の整数 = 0x4000 | 450 = 0x41C2（2 B） / 1 + 2 + 450 = 453 / STREAM フレーム 0x09 0x00 で + 2 = 455
          / 見出し 1 + 8 + 1 = 10 / 10 + 455 + 16 = 481 / UDP + 8 = 489 = 0x01E9 / IP + 20 = 509 = 0x01FD / + 18 = 527 / + 8 = 535
          / 535 × 8 = 4,280 ビット / 4.28 µs → 4.3 µs
GRE:      521 + 4 + 20 = 545 = 0x0221 / QUIC 509 + 24 = 533 = 0x0215
ポート:   51235 = 0xC823、51234 = 0xC822、443 = 0x01BB、40002 = 0x9C42、40001 = 0x9C41
番号:     192.168.1.10 = C0 A8 01 0A、142.250.196.110 = 8E FA C4 6E、203.0.113.5 = CB 00 71 05
欄:       TCP のヘッダ長 5 とフラグ ACK・PSH = 0101 0000 0001 1000 = 50 18 / IPv4 の版とヘッダ長 = 45、DF と断片位置 0 = 40 00、
          TTL 64 = 40、プロトコル 6 = 06・17 = 11・GRE 47 = 2F / GRE の見出し 00 00 08 00
ビット:   各バイトを下位のビットから並べる。0x55 → 10101010、0xD5（SFD）→ 10101011、
          宛先 MAC 02 11 22 33 44 01 → 01000000 10001000 01000100 11001100 00100010 10000000
```

QUIC のパケット 481 B と TLS のレコード 481 B が同じなのは偶然（HTTP/3 の見出しが HTTP/2 より 6 B 短く、QUIC の見出し＋STREAM フレームが TLS の見出し＋種別より 6 B 長い）。それぞれの内訳を下の欄に出した。

## 模式にした所

- 枠の幅はバイト数に比例しない（図の説明に書いた）。段階6 の線の速さだけはバイト数に比例させた（下の欄の題に書いた）。
- 要求 1 つが、レコード 1 つ・セグメント 1 つ・パケット 1 つに収まる形にした（459 B は MSS 1,460 B より小さい）。接続の最初に送る HTTP/2 の前置き・SETTINGS・WINDOW_UPDATE、HTTP/3 の制御と QPACK のストリームは省いた（注記）。
- TCP はオプションの無い 20 B（第11章と同じ）。Linux は相手が応じればタイムスタンプ 12 B を付けるが、Google の側が応じるかは確かめていないので書かない（注記は「オプションの無い 20 B で描いた」）。
- QUIC は接続後の短いヘッダ（1-RTT）。接続 ID 8 B・パケット番号 1 B は例。0-RTT や最初のパケット（長いヘッダ、第18章 場面1 の 1,278 B の例）は別の形。
- PC は Ethernet でつないだ形（第11章 場面3 と同じ）。Wi-Fi は段階5 の文で 1 句だけ。
- ビット列は MAC の送る順（各バイトの下位から）まで。1000BASE-T の符号（PAM-5）や電圧は部品 line-code へ印で渡す。
- 番号・確認応答番号・ウィンドウ・チェックサム・FCS・接続 ID・タグ・識別子は接続ごとに変わるので、値の代わりに中身を書いた（図の説明）。IPv4 のヘッダチェックサムも識別子に頼るので値を書かない。
- GRE の見出しは RFC 2784 の最小の 4 B。外側の IPv4 は全長とプロトコルと送信元・宛先だけを書き、TTL などは書かない。拠点の中のリンクの包み（Ethernet など）と、家から拠点までの区間の包みは省いた（図の境目の札）。Maglev と GFE の番号は非公開なので 10.0.0.2・10.0.1.2 の私設アドレスの例（共通の例の RFC 5737 の範囲は家・ISP・第三者に割り当て済みのため）。

## 確かめたこと

- 4 つの姿（既定・`via=quic`・`gre=1`・`gre=1&via=quic`）の全段階の写真（1920×880）と縦読み版（図は横にスクロールする作り）、時刻を指定した写真（段階6 の線の 0.3・1.5・4.2 秒、GRE の段階6 の 1.9・2.2・3.0 秒）、止めた姿（段階6 の線がプリアンブルの終わりに止まる、GRE の外した枠が破線で残る）、ダーク 3 枚（QUIC の段階2、既定の段階6、GRE の段階5）を見た。重なり・はみ出し・消し忘れ・色の意味（ヘッダは無彩色、足したものは x、データと暗号文とビットは d）を確かめた。
- 最初の写真で、段階の文が図の値（バイト数・欄の値）を繰り返していたので、文は理由（なぜ種別がいつも 23 か、なぜ番号が 1 でないか、なぜ宛先 MAC がルーターか、なぜ GRE が要るか）に書き直し、値は図の行と下の欄だけにした。下の欄の題の「（ブラウザ）」「（OS が付ける）」も、図の境目と重なるので消した。
- 部品の中の印（既定 10 個・QUIC 10 個・GRE 9 個）を `--drill` で開いた。line-code へは段階1 で開く（line-code は同時に作られていて、最後の検証の時点の版で開けた。line-code の段階1 の中身が変わったら、つなぎの一文「PHY はこのビット列を 1 バイトずつ受け取り、電圧・光・電波の記号に変えて送る」と合うかを仕上げ確認で見る）。

## 迷った所と決め方

1. **TCP＋TLS の要求の中身。** 指示の案は「第11章 場面3 の 300 バイトの要求文の例に TLS を足した姿」と「HTTP/2」の両方を挙げていた。300 B は HTTP/1.1 の文字の要求文で、HTTP/2 では HPACK で縮めたバイト列になるので、両方は同時に満たせない。視聴ページは HTTP/2 で取る（共通の例・第21章・第25章）ことと、大きさに出どころがある（第21章 場面3 の 450 B）ことから、HTTP/2 の 459 B にした。第11章との差は印のつなぎの一文で言う。
2. **QUIC の姿。** 指示の案は「動画の断片: HTTP/3 → QUIC → UDP 51234 → 443」。次の 3 つの理由で、www.youtube.com への同じ GET /watch を HTTP/3 で送る姿（51234 → 142.250.196.110:443）にした。(a) 51234 の QUIC は第18章 場面1・第19章 場面1・第20章 場面6・第14章 場面4 で www.youtube.com との接続で、配信元への QUIC は第19章 場面1 の表で 51236 → 198.51.100.80（fd 31）。断片にすると、ポートか宛先が章と食い違う。(b) 断片の POST は長い URL と 1.4〜1.6 KB の本文で 2 個以上のパケットに分かれ、ヘッダを縮めた大きさの実測も無い。(c) 同じ要求を 2 つの道で包むと、足すバイトの違いをそのまま比べられる（フレーム 539 B と 527 B）。断片の POST は段階3 の文で「同じ順に包む」と書き、第10章 場面6 の印のつなぎの一文も「fetch の要求も」で受けた。Alt-Svc を覚えた後は視聴ページも HTTP/3 になる（第21章 場面4 の図も要求 1 /watch がストリーム 0）。
3. **GRE の段階の割り振り。** 段階の数を 6 にそろえるため、段階1〜4 は via の姿のまま（PC が作った層）、段階5 で Maglev が包み、段階6 で GFE が外す形にした。NAT と TTL の変化（203.0.113.5:40002、TTL 55）は段階5 の下の欄に出し、PC の段階1〜4 の値は変えない。Maglev の段階に Ethernet を描かないのは、拠点の中のリンクが公開されていないため。GFE の番号の例は、共通の例の RFC 5737 の範囲が家・ISP・第三者に割り当て済みなので、RFC 1918 の 10.0.0.2・10.0.1.2 にした。
4. **プリアンブルの役目の書き方。** 第13章 場面3 段階2 の「拍を合わせる」は 10BASE-T の説明で、1000BASE-T ではフレームの間も符号を流し続ける（plan.md「後で見直す所」で未確認のまま）。部品では「SFD の最後の 11 が本体の始まりの印」だけを書き、プリアンブルの印のつなぎの一文もそれに合わせた。
5. **段階の文と下の欄の分け方。** 初めの版は、段階の文が下の欄の値（ポート・プロトコル番号・長さ）を言い直していた。文は「なぜ」（種別がいつも 23 の理由、番号が 1 でない理由、宛先 MAC がルーターの理由、VIP だから GRE が要る理由、DSR の理由）に絞り、値は図にだけ置いた。
6. **QUIC のパケット番号と接続 ID の長さ。** 規格では 1〜4 B・0〜20 B。quiche の既定（接続 ID 8 B）と、接続の初めに quiche が選ぶ長さ（1 B）を例にし、下の欄と注記に「1〜4 B」「例」と書いた。この結果、QUIC のパケットが TLS のレコードと同じ 481 B になったが、内訳が違うので変えていない。
7. **動き。** 意味のある動きは「送る順と、時間がバイト数に比例すること」（段階6 の線）と「外側を外す」（GRE の段階6）の 2 つに限った。ヘッダが付く様子を動かす案は、第11章 場面3 と同じく止めた図で足りるのでやめた。

### line-code とのつなぎ

line-code の段階1（既定の pam5）は「PHY は MAC から 1 バイトずつ受け取る」で始まり、例のバイトは 02（宛先 MAC の先頭）、図は 1 バイトが 1 拍 8 ns で対 A〜D の段階の組になる形。前のつなぎの一文「PHY はこのビット列を 1 バイトずつ受け取り、電圧・光・電波の記号に変えて送る」は段階1 の 1 文目の言い直しで、印は params を渡さないので板には銅線（PAM-5）だけが出るのに光・電波も挙げていた。また encap の段階6 の「下位のビットから送る」と、line-code の「8 ビットを 1 拍でまとめて送る」がつながっていなかった。新しい一文「このビット列は、1 Gbps の銅線では 8 ビットずつ 1 拍 8 ns で 4 対の段階の組になる」で、encap の列（下位から並べた MAC の順）と line-code の 1 拍 1 バイトをつなぎ、line-code の段階1 の語（4 対の段階の組、1 拍 8 ns）で終えた。02 は encap の下の欄の宛先 MAC の先頭と同じ値。

### 確かめたこと

- 事実: RFC 8446 §5.2（外の種別はいつも 23、版 0x0303、追加データは見出し 5 B）、RFC 9001 §5.4（短いヘッダは先頭 1 B の下位 5 ビットとパケット番号を隠す）、RFC 9000 §14（IPv4 では DF を立てる）・§19.8（STREAM の 0x08〜0x0f、OFF・LEN・FIN）、RFC 9113 §4.1・§6.2、RFC 2784（最小 4 B、種類 0x0800、IP のプロトコル 47）を、段階の文・下の欄・新しいつなぎの一文の言い切りと照らした。Maglev の論文（NSDI 2016、PDF を取って §2.1・§4.3 を読んだ）で、VIP は特定の装置に付かず Maglev の後ろの複数の行き先が受けること、行き先宛ての外側の IP ヘッダを付けた GRE で包むこと、行き先で外して受け取り、応答は送信元を VIP にして返すこと（DSR）、GRE の recursion control の欄は断片を 1 回だけ回すために使うことを確かめた。GRE の見出しの欄（鍵・番号の有無）は論文に無いので、4 B は RFC 2784 の最小の形の例のまま（記録の「模式にした所」の通り）。1000BASE-T の IDLE は上の表の通り。
- 値: 459 → 481（レコードの長さ 476 ＝ 0x01DC）→ 501 → 521（0x0209）→ 539 → 547（4,376 ビット、4.4 µs）、QUIC 453（長さ 450 ＝ 0x41C2）→ 481（10 ＋ 2 ＋ 453 ＋ 16）→ 489（0x01E9）→ 509（0x01FD）→ 527 → 535（4,280 ビット、4.3 µs）、GRE 545（0x0221）・533（0x0215）を計算し直した。ポート（0xC823・0xC822・0x01BB）、番号（C0 A8 01 0A・8E FA C4 6E）、45・40 00・40・06・11・2F、TCP の 50 18、GRE の 00 00 08 00、送る順のビット（55 → 10101010、D5 → 10101011、02 11 22 33 44 01 → 01000000 10001000 01000100 11001100 00100010 10000000）も合っていた。第21章 場面3 の見出し 00 01 C2 01 05 00 00 00 01・HPACK 450 B・682 B、第20章 場面6 のレコードの作り、第11章 場面3 の 20・20・14・4・8 B、第18章 場面1 の欄、第25章 場面3 の 203.0.113.5:40002・TTL 55、第22章 場面3 の Maglev 2・GFE 2 と照らした。
- 判断: TCP＋TLS の要求を第21章 場面3 の 459 B にしたこと、QUIC の姿を同じ GET /watch にしたこと（第14・18〜21章の 51234 → 142.250.196.110:443 と合う）、QUIC のパケットとレコードが偶然どちらも 481 B になったこと（内訳を図と下の欄で分けている）、Maglev と GFE を RFC 1918 の例にしたこと、プリアンブルの役目に触れなかったことは、どれも妥当と判断した。
- 図: 4 つの姿の全段階の写真（1920×880、縦読み版）、時刻を指定した写真（段階6 の線の 0・0.3・1.5・2.5・4.2・5.5 秒、GRE の段階6 の 0.5・1.9・2.2・3.0・3.8 秒）、止めた姿（線はプリアンブルの終わり、GRE の外した枠は破線で残る）、ダーク 3 枚（QUIC の段階2、既定の段階6、GRE の段階5）を見た。重なり・はみ出し・消し忘れ・色の意味（ヘッダは無彩色、足したものは x、データ・暗号文・タグは d）・止まる位置に問題は無かった。時期の合わない表示も無い（GRE の段階5 の中の値は NAT の後の 203.0.113.5:40002・TTL 55 で、段階1〜4 の PC の値と分けてある）。
