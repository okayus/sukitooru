# 部品 mmu-walk（ページの表を引く）の記録（2026-11-18、P5）

[共通の指示書](2026-11-18-p5-brief.md) の部品 mmu-walk。部品は `assets/parts/mmu-walk.js`、見本は `parts.html?part=mmu-walk`。layer は `cpu`、home は `09-os.html#s4`。

## 設計

第9章 場面4 の仮想アドレス 0x00007f3a2c41_1b20 を、CPU の MMU が 9・9・9・9・12 ビットに切り、CR3 から 4 段の表を 1 段ずつ読んで物理アドレス 0x1a2b4b20 を作り、TLB に控える。段階5 で項の印の照らし合わせと #PF、段階6 で IOMMU（Intel VT-d）を見せる。

物理ページの箱に番地と中身の位置を出すのは、アクセスが通る none だけ（許さないアクセスは物理ページへ進まない。④ → 物理ページの矢印も出さない）。

規則の行は、そのアクセスで見ない印を薄く、違反を x にする（読むときは R/W と NX を見ない、など）。既定を p にしたのは、本文の最初の規則（P = 0）で、第9章 場面4 段階4 の札と同じ番地だから。使う所は例ごとに 1 か所ずつで、数では決まらない。

色: x はいま切る欄・いま読む項・違反・注目の CR3、d は読み終えた項・項が指す矢印・TLB のヒット・物理ページの中身。e・h・p・r は使わない。

### 番号の計算（node の BigInt で計算した）

| 番地 | VA >> 39 & 0x1FF | VA >> 30 & 0x1FF | VA >> 21 & 0x1FF | VA >> 12 & 0x1FF | VA & 0xFFF | VA >> 12（VPN） |
|---|---|---|---|---|---|---|
| 0x00007f3a2c41_1b20 | 0x0fe | 0x0e8 | 0x162 | **0x011** | 0xb20 | 0x7f3a2c411 |
| 0x00007f3a2c41_1b28 | 0x0fe | 0x0e8 | 0x162 | 0x011 | 0xb28 | 0x7f3a2c411 |
| 0x00007f3a2c43_1000 | 0x0fe | 0x0e8 | 0x162 | 0x031 | 0x000 | 0x7f3a2c431 |
| 0x00007f3a2d82_8000（仕上げ確認） | 0x0fe | 0x0e8 | 0x16c | 0x028 | 0x000 | 0x7f3a2d828 |
| 0xffffc90000a0_0000（仕上げ確認） | 0x192 | 0x000 | 0x005 | 0x000 | 0x000 | 0xc90000a00（ビット 47:12） |
| 0x1000（DMA） | 0x000 | 0x000 | 0x000 | 0x001 | 0x000 | 0x000000001 |
| 0x1a2b4b20（DMA） | 0x000 | 0x000 | 0x0d1 | 0x0b4 | 0xb20 | 0x00001a2b4 |

- 2 進: 0x00007f3a2c411b20 の下位 48 ビット = 011111110｜011101000｜101100010｜000010001｜101100100000。ビット 47 は 0 なので、上位 16 ビットも 0（4 段のときの正しい形）。
- 項の番地 = 表の先頭 + 番号 × 8: 0x05d27000 + 0x0fe × 8 = 0x05d277f0、0x0b8e1000 + 0x0e8 × 8 = 0x0b8e1740、0x13f6a000 + 0x162 × 8 = 0x13f6ab10、0x0e0c9000 + 0x011 × 8 = 0x0e0c9088。
- 物理アドレス: 0x1a2b4 × 0x1000 + 0xb20 = 0x1a2b4b20（0xb28 なら 0x1a2b4b28）。
- NIC: 0x2b7c4000・0x31a09000・0x0f6d2000（番号 0）、0x2e815000 + 0x001 × 8 = 0x2e815008 → 0x3d0e2000。0x1a2b4b20 は ③ の項 0x0f6d2000 + 0x0d1 × 8 = 0x0f6d2688 が R0 W0。
- 段階5 の表（仕上げ確認で計算し直した）: p は 0x0e0c9000 + 0x031 × 8 = 0x0e0c9188 が P0。rw は 0x13f6a000 + 0x16c × 8 = 0x13f6ab60 → 0x15c37000、0x15c37000 + 0x028 × 8 = 0x15c37140 → PFN 0x0a7c3。us は 0x05d27000 + 0x192 × 8 = 0x05d27c90 → 0x0270c000（番号 0）→ 0x0381e000 + 0x005 × 8 = 0x0381e028 → 0x1f4a6000（番号 0）→ PFN 0xfeb00。0xffffc90000a0_0000 はビット 63:47 がすべて 1 で、4 段のときの正しい形。
- 第9章 場面4 の図は PT の欄を 0x01b、TLB の VPN を 0x7f3a2c41・0x7f3a2c42 と書いていた（調整役が直した）。計算では 0x011 と 0x7f3a2c411・0x7f3a2c412（VPN は VA >> 12 の 36 ビット = 16 進 9 桁。図の値は VA >> 16 の桁）。部品は計算どおりにした（下の「章で直したほうがよい所」）。

## 事実の出どころ（2026-11-18 に確かめた）

- Intel SDM Vol. 3A（Order 253668-093US、2026-09。https://cdrdv2.intel.com/v1/dl/getContent/671190 を pdftotext で読んだ）。この版ではページングが第5章に移っていて、指示書の 4.5・4.6・4.10 は前の版の番号に当たる。
  - 4.5 Canonicality Checking: 4 段のとき、ビット 63:47 が同じでない番地への読み書きは例外（多くは #GP、スタックは #SS）。
  - 5.5.2・5.5.4: CR3 の M−1:12 が PML4 の物理アドレス。各段の項の物理アドレスは、ビット 51:12 が前の段（CR3 か項）、11:3 が線形アドレスの 9 ビット、2:0 が 0（＝ 表の先頭 + 番号 × 8）。表は 4 KiB に 64 ビットの項 512 個。P = 0 の項を使う番地には変換が無く、触れると #PF。最後は PTE の 51:12 と線形アドレスの 11:0。5 段（LA57）は CR4.LA57 = 1 のとき 57 ビット。
  - 5.6.1: U/S が 1 つでも 0 ならスーパーバイザの番地で、ユーザーモードは読み・書き・実行のどれもできない。ユーザーモードの書き込みは全段の R/W が 1 のときだけ。IA32_EFER.NXE = 1 なら、全段の XD が 0 のときだけ命令を取り出せる。照らし合わせは TLB とページ構造キャッシュの印で行ってよい。
  - 5.7: #PF は例外 14。変換が無いか、権利が合わないときに起き、CR2 に線形アドレスが入る。
  - 5.10.2: TLB の 1 行はページの番号 → ページフレームと、R/W の AND・U/S の AND・XD の OR。P = 1 の変換だけを控える。ヒットすれば表を読まないことがある。行は PCID ごと。
  - 5.10.3: PML4E・PDPTE・PDE のキャッシュ（ページ構造キャッシュ）。TLB に無くても途中の段から引ける（注記の「4 回読むとは限らない」）。
- Intel VT-d 仕様 Rev. 5.20（D51397-019、2026-04。https://cdrdv2-public.intel.com/919688/D51397-019-vt-directed-io-spec.pdf）
  - 3.4.1: 要求の出どころ（source-id）は PCIe の Requester ID（バス・装置・機能）。
  - 3.4.2: legacy mode では、ルート表（バス番号で 256 項）→ コンテキスト表（装置・機能で 256 項）→ その装置の second-stage の表。
  - 3.5: どの段の表も 4 KiB に 8 バイトの項 512 個。図 3-5 は 48 ビットの番地を 9・9・9・9・12 で引く（番号を 3 ビット左へずらして先頭に足す図）。
  - 3.6: first-stage は Intel 64 の CPU と同じ形の表。3.7: second-stage の段の数は AGAW で決まり、9 ビットずつ引く。9.8: second-stage の項の印は R（ビット 0）と W（ビット 1）。表 30 の SSS.2: R = W = 0 の項は変換の失敗。3.7.1: 書き込みは全段で書きを許すときだけ。
  - 6.2.4: IOTLB に変換を控える。7.1.1: 変換に失敗した要求は止める（書き込みは捨てる）。7.2・7.3: フォールト記録レジスタに記録し、割り込み（MSI）で知らせる。
- Linux（GitHub の torvalds/linux master、2026-11-18 に読んだ）
  - `arch/x86/include/asm/pgtable_types.h`: `_PAGE_BIT_PRESENT` 0・`RW` 1・`USER` 2・`NX` 63。`_PAGE_TABLE` = P・RW・USER・A・D（上の段の項は NX = 0）。`PAGE_SHARED` = P・RW・USER・A・NX、`PAGE_READONLY_EXEC` = P・USER・A。
  - `Documentation/arch/x86/x86_64/mm.rst`: 4 段のとき vmalloc/ioremap の範囲は 0xffffc90000000000 から（CONFIG_RANDOMIZE_MEMORY で動く）。
  - `Documentation/arch/x86/x86_64/5level-paging.rst`: 5 段でも、既定では 47 ビットより上に番地を置かない（ヒントの番地で頼めば置く）。
  - `Documentation/arch/x86/pti.rst`: PTI を使うと、ユーザーモードの表にはカーネルへの出入りに要る分しか載らない。
  - `drivers/iommu/intel/iommu.c`・`Kconfig`: scalable mode はハードウェアが対応していれば既定で有効（`INTEL_IOMMU_SCALABLE_MODE_DEFAULT_ON` は default y）。first-stage と second-stage の両方があれば first-stage を使う（`first_level_by_default`）。legacy mode では second-stage だけ。

## 模式にした所

- 項は「次の表（か物理ページ）のページの番号」と P・R/W・U/S・NX だけ。A・D・G・PWT・PCD・保護キーなどは省いた（図の説明）。大きなページ（2 MiB・1 GiB）も省いた。
- 表を読む回数は、ページ構造キャッシュを使わない 4 回（注記で「4 回とは限らない」）。TLB は第9章と同じ 3 行だけ。L1・L2 の TLB と PCID は描かない。
- 照らし合わせは 4 段をまとめた印（R/W・U/S の AND、NX の OR）で描いた。
- IOMMU は VT-d の legacy mode と second-stage の形（印は R・W）。図の説明に「IOMMU は VT-d の second-stage 変換の形（印は R・W）」と書いた。段の数は AGAW で決まり、図は 48 ビット・4 段。
- us の例（NIC のレジスタを写したページ、U/S = 0）は PTI を使わない場合の姿。PTI を使う Linux では、ユーザーモードの表にそのページは載らず（P = 0 と同じ扱い）、どちらでも #PF になる。部品には書いていない（字数。迷った所 5）。
- 動きは、欄の切り出し・項を 1 つずつ読む・TLB に書く・照らし合わせの例を順に光らせることだけ。読み出しの拍数は描かない。

## 確かめたこと

（検証の最終結果は下の節。ここは途中で見つけて直したもの）

- 写真（1920×880、全段階の止めた姿と時刻指定、縦読み版、ダーク）で見て直したもの:
  - CR3 の矢印（x = 155 を上る）が CPU の箱の副題「番地を変換し、印を照らし合わせる」を横切っていた → 副題を x 166 へ。
  - TLB の行の「VPN → PFN」と印「RW1 US1 NX1」が 204px の行に入りきらない計算だった → TLB の箱を 240px に広げ、照らし合わせの箱を 206px にして、アクセスの文を短くした。
  - 段階6 で、0x1000 の表を引いている間から結果「W = 1 で書ける」と、まだ引いていない 0x1a2b4b20 の結果が出ていた（時期の合わない表示）→ 結果の行は、その例を引き終えてから出す。動いているときは、いま引いている例の行だけを出す。
  - 段階5 で「表を読んだ回数」が空のまま残っていた → 段階5 では箱ごと薄くする（例ごとに回数が違うため）。
  - 段階3 の最後（4 段とも読んだ後）も TLB の欄が「表を引いている」だった → 「表を 4 段とも引いた」。
  - 段階1 の TLB の欄は、TLB を探している間（最初の 1.6 秒）だけ x にする。

1. **IOMMU を params にするか、最後の段階にするか** → 最後の段階（6）にした。params にすると 6 段階の別の流れ（本文と図）が要る。最後の段階なら、第7章 場面4 段階5 から開いた読者が ‹ で CPU の側の同じ形を見られる。同じ図の同じ表の枠に NIC の表の値を出し、「表の形が同じ」を位置で見せた。

4. **IOMMU の項の形。** VT-d には CPU と同じ形の first-stage と、印が R・W の second-stage がある。Linux は対応するハードウェアでは first-stage を既定で使う。図は legacy mode の second-stage にした（どの VT-d でも使える。ルート表 → コンテキスト表 → 表の道が 1 本で描ける。「同じ形の表で、印だけ違う」が見える）。図の説明に形を書いた。

### 直さなかったが気になる点

1. 段階5 の部品の中の印「例外 #PF」の札は、通る例（none）でも結果の行の横に出る。印は段階ごとに出し入れするので、例ごとには消せない。
2. 段階6 の IOMMU の項は legacy mode の second-stage（印 R・W）の形。Linux は scalable mode を備えた VT-d では first-stage（CPU と同じ形の項）を既定で使う（上の Kconfig と `first_level_by_default`）。図の説明で「second-stage 変換の形」と限っているので、模式として残した。
3. 段階5 の us は PTI を使わない姿（項があって U/S = 0）。PTI を使う CPU では、アプリの表にこの項が無く P = 0 で #PF になる。部品には書いていない（注記の字数）。印のつなぎの一文で両方をつないだ。
4. 部品の中の印「TLB」（→ 第6章 場面6 段階2）のつなぎの一文「CPU の中の SRAM に置いた小さな写し」は、TLB の作り（SRAM のセルの配列と、全部の行と比べる回路）を SRAM と縮めている。行き先の段階が SRAM の話なので残した。
