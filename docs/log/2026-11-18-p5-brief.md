## 部品とは

章の図の要素に付いた**掘り下げの印**（↓ の札）を押すと、場面の上に**板**が重なり、一つ下の層を見せる。板の中身は、下の章の場面の埋め込みか、**部品**（`assets/parts/<名前>.js`）。部品は、章の場面に説明が無い仕組み（P4 の棚卸しの「無い」）や、説明はあるが例の値が上の章と違う所（「例が違う」）を埋める小さな場面で、**上の章の例の値のまま**動く。手本は `assets/parts/cpu-mode.js`（第9章 場面3 の `syscall` の下の層。第6章の YT-8 にモードのビットを足した模式図）。

## 仕事

1. **部品を作る**: `assets/parts/<名前>.js` の雛形（「準備中」）を書き換える。
2. **記録を書く**: `docs/log/2026-11-18-p5-<名前>.md` に、設計（段階の表・params・例の値とその出どころの章）、事実の出どころ（一次資料の URL と、何を確かめたか）、模式にした所、確かめたこと、**印の張り替えの表**（下記）、迷った所と決め方、章で直したほうがよい所を書く。
3. **検証**: 下の「検証」を全部通す。

**章のファイルは変えない。** 章への印（張り替え・足し）は、全部の部品の仕上げ確認が済んでから、別の担当がまとめて張る。あなたは張るための表を書く。

## 部品の決まり（authoring.md §5.5 に足すもの）

- `YT.parts.define('名前', { title, layer, home, lead, caption, note, steps, setup, onStep, frame })`。
  - `title`: 部品の名前（板の道筋と parts.html の見出しに出る。15 字まで）。
  - `layer`: 部品が見せる仕組みの層（`assets/layers.js` の id）。**使う所の層から down をたどって届く層**にする（印の向きが「下」になる）。`node tools/drillcheck.mjs` の向きの判定と同じ。
  - `home`: 「章を開く ↗」の行き先（いちばん近い章の場面。`06-cpu.html#s3` の形）。
  - `lead`: parts.html の場面のリード（110 字まで）。1 文目は「何を見せるか」（表紙の構成にも出る）、2 文目でどの上の場面から掘るか。
  - `caption`: 図の説明（「図　」で始める。120 字まで）。模式にした所はここか note に書く。
  - `note`: 注記（140 字まで）。章の補足に当たる。
  - `steps`: 4〜6 段階。**1 段階を 1 行**（`{ title: '…', text: '…' },`）で書く（xrefcheck・lencheck がこの行を数える）。本文 160 字まで。params で中身を変えるなら、`steps: function (p) { return p.via === 'quic' ? STEPS_QUIC : STEPS_TCP; }` のように、変わり方ごとの配列を 1 行 1 段階で書いて選ぶ（段階の数はそろえる）。
- 段階の本文に、他の章へのリンクの記法（`[[13-ethernet.html#s4|…]]`）を使わない（板の中で押すとページごと移る）。章は「第6章 場面3」と文字で書いてよい。下の層へは図の印で掘らせる。
- 図: viewBox `0 0 960 560`、文字は `t-xs`（10px）以上。段階が進んでも部品の位置を変えない。色の意味は全章で固定（e 電子・電流・電気信号、h 正孔・＋電荷・高い電位（論理回路の 1 の線）、p 光、r 電波、d データ・パケット・ビット列、x 強調・変化・注意）。区別のためだけに e・h・p・r を使わない（authoring.md §9）。
- **値**: 上の章の例の値をそのまま使う（差し込みに挙げた値と、使う所の段階の値）。使う所どうしで値が食い違うときは、多くの上の場所に合う値を選び、違う場所は記録に書く（params で切り替えるか、張り替えの表の「つなぎの一文」で差を言う）。値を計算で決める所（ビット・ヘッダの欄・番地の切り方）は計算して確かめ、記録に計算を書く。
- **止めたときの姿**（`YT.motion.playing` が false）に、その段階の要点（値・結果）が出ていること。動きは「意味のある動き」だけ。粒を `Math.random` で散らさない。
- `onStep` は段階の見た目を全部決める。`frame` は `dt = 0` でも正しく描く。cpu-mode のように、段階の中の小さな場面（ph）を `U.seq(ctx.ts, […], true)` で回すなら、書き換えの判定に段階・場面・立ち上がりを過ぎたかを入れる（時刻が飛んでも書き換えを落とさない）。
- **部品の中の印**: 部品の setup の中で `ctx.mark(st.xxx, { to: '05-kioku.html#s2.3', label: '…', at: [x, y], steps: [1, 2], bridge: '…' });` を 1 行に 1 つ。行き先は、部品の図の要素が頼っている仕組みを説明している、すぐ下の層の章の場面・段階か、ほかの部品（`part: 'alu', step: 2`）。1 段階に出る印は 3 つまで。つなぎの一文は 60 字まで（上の語で始めて下の語で終える）。
- **params**: 印から渡す値（`params: { via: 'quic' }`）。部品の中では `ctx.params.via`。無いときの既定は、いちばん多くの使う所に合う値にする。parts.html では既定の姿が出る（`parts.html?part=<名前>&via=quic` で ほかの姿を出せる）。
- 部品のファイルの先頭のコメントに、何の部品か・使う所・値の出どころ・事実を確かめた資料と日付を書く（cpu-mode と同じ形）。
- 事実は一次資料（規格・仕様書・メーカーの手引き・Linux のソースと文書）で確かめる。WebSearch / WebFetch は ToolSearch で読み込んで使う。確かめられないことは書かないか弱める。年や版で変わることは「2026 年時点」「Linux 6.x では」と限る。資料の文をそのまま写さない。

## 印の張り替えの表（記録のファイルに書く）

部品を使う上の場所ごとに 1 行。差し込みに挙げた場所（P4 の表の「例が違う」「無い」の行）を全部見て、ほかにも部品が合う所があれば足す。いまの印は `node tools/drillcheck.mjs --list chapters/NN-*.html` で見る。

| 上（章 場面.段階） | 図の要素（章のコードの変数。無ければ何に付けるか） | いまの印（行き先） | 新しい印（part・step・params） | 張り替え／足す | つなぎの一文（60 字まで） | label（20 字まで） | 札の位置の案 [x, y] |
|---|---|---|---|---|---|---|---|
| 09 s3.3 | st.kQueue（受信キュー） | 07-shuuhen.html#s4.3 | part: 'nic-rx', step: 2 | 張り替え | 受信キューのデータは、NIC が DMA で書いた 1,452 B の断片 | 受信キュー | [404, 492] |

- 「張り替え」は、いまの印の行き先を部品にする（例が違う → 有る）。「足す」は、印の無い所に新しく張る（無い → 有る）。いまの印のほうが行き先として良ければ「そのまま」と書き、理由を書く。
- 1 つの段階に出る印は 3 つまで（足すと 4 つになる所は、どれを替えるかを書く）。
- つなぎの一文は、上の段階の語で始めて、部品の段階の語で終える。部品の例の値と食い違う値を書かない。

## 検証（完了の条件）

1. `node tools/lencheck.mjs assets/parts/<名前>.js` — 超過なし。
2. `node tools/xrefcheck.mjs assets/parts/<名前>.js` — 問題 0 件。
3. `timeout 900 node tools/verify.mjs --nav --overlap --drill 'parts.html?part=<名前>'` — ✓。段階の行き来「違いなし」、文字の重なり「なし」、掘り下げの ✗ なし、JS のエラーなし。params の姿ごとにも走らせる（`'parts.html?part=<名前>&via=quic'`）。
4. 写真: `timeout 900 node tools/verify.mjs --shots <一時置き場>/shots --all-steps 'parts.html?part=<名前>'` で**全段階の写真を全部** Read ツールで見る。文字の重なり、はみ出し、消し忘れ、色の意味違い、止まる位置。縦読み版（`-phone`）も見る。動く札・途中で書き換わる文字は `timeout 300 node tools/shot.mjs 'parts.html?part=<名前>' --scene 1 --step K --at 0,1.5,3 --out <一時置き場>/at` で、止めた姿は `--paused` で撮って見る。`--dark` で 2〜3 枚。
5. 板の中の姿: 部品は章の印から板で開くと、左に段階の文、右に図が出る（parts.html の場面とほぼ同じ幅）。parts.html で 1920×880 と 1280×688 の両方で収まっていれば板でも収まる。

## 守ること

- 変えてよいのは、自分の部品のファイル（`assets/parts/<名前>.js`）と自分の記録のファイルだけ。engine.js・base.css・tools/・parts.html・章・ほかの部品・ほかの docs は変えない（直したほうがよい所は報告に書く）。部品に足りない描き方は、部品のファイルの中に関数で書く。
- ほかの担当が同時にほかの部品を作っている。parts.html を引数なしで検証すると、作りかけのほかの部品が混ざるので、必ず `?part=<名前>` を付ける。`--drill` で開いた章の埋め込みにエラーが出たら、少し待って走らせ直す。
- tools/serve.sh は使わない。verify.mjs は必ず `timeout 900`、shot.mjs は `timeout 300` を付けて走らせる。Chrome のプロセスを名前で止めない（pkill・killall を使わない）。
- 写真と一時ファイルは一時置き場にだけ置く。プロジェクトの中に置かない。一時置き場は消えることがあるので、記録はプロジェクトの記録のファイルに書く。
- サブエージェントを呼ばない。git の commit・push をしない（調整役がする）。

## 仕上げ確認（別の担当への指示）

部品を作った担当とは別の担当が、部品 1 つ（または組）を読者と校閲者の目で確かめ、直す。cpu-mode の仕上げ確認（docs/log/2026-11-17-p2.md「部品 cpu-mode の仕上げ確認」）と同じ。

- 読むもの: 上の「最初に読むもの」と、作った担当の記録（`docs/log/2026-11-18-p5-<名前>.md`）、部品のファイル。
- 確かめること:
  1. **事実**: 段階の文・図の札・注記の事実を、一次資料で確かめ直す（作った担当の出どころを読むだけでなく、言い切りが資料の範囲を越えていないか）。年・版で変わる事実の限り方。
  2. **値**: 上の章の例の値との一致（使う所の段階の本文と図を読んで突き合わせる）。計算した値（ビット・欄・番地）を計算し直す。
  3. **図**: 全段階の写真（1920 幅・縦読み版・ダーク）、時刻を指定した写真、止めた姿。重なり・はみ出し・消し忘れ・色の意味・止まる位置・時期の合わない表示（cpu-mode では「起動時の wrmsr の間に A = 45」が見つかった）。
  4. **文章**: authoring.md §8・§9（結論先行、一文一義、言い換え・比喩なし、同じ情報の二重の表示なし、字数）。
  5. **印の張り替えの表**: つなぎの一文が上の段階と部品の段階をつないでいるか、値が食い違っていないか、行き先の段階が正しいか。
- 直してよいのは、その部品のファイルと記録のファイル（記録には「仕上げ確認」の節を足し、直した所を全部書く）。章・ほかのファイルは変えない（報告に書く）。
- 検証は上の「検証」と同じ。最後の報告に、直した所の一覧、直さなかったが気になる点、「検証済みにしてよいか」を書く。
