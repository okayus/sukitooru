# 2026-11-15 日刊のノートの仕組み

依頼は「トレンドの技術ニュースを毎日 1 つ解説したページを作成して欲しい。claude の 100$ プランと chatGPT 30$ プランには契約してるので、どういう定時タスクでどういうワークフローにするかを調査して」。調査の結果を出した後、持ち主が次の 3 つを決めた。

- マージは自動。
- 日刊は予想なしで作る（予想 → ノート → 差の手順は、詳しいノートに残す）。
- 話題は、Web プラットフォーム・言語・OS・ネットワーク・セキュリティ。AI の製品の話題は外す（一旦）。

毎朝の実行の手順は [../daily-news.md](../daily-news.md)、ノートの型は [../../news/README.md](../../news/README.md) の「日刊の型」。

## 仕組み

1. 毎朝、Claude Code のクラウドの scheduled task（旧 routines）が起動し、リポジトリを clone して `docs/daily-news.md` を実行する。
2. `tools/news-candidates.mjs` が、Hacker News の front page・はてなブックマーク（テクノロジー）・Lobsters から候補を集める。
3. Claude が 1 件選び、一次情報を読んで `news/YYYY-MM-DD-題.md` を書き、`build-news.mjs` と `verify.mjs` を通す。
4. `claude/news-<実行した日>` に push し、プルリクエストを出す。
5. GitHub Actions（`.github/workflows/news-pr.yml`）が検査し、通ればスカッシュでマージして、GitHub Pages を作り直させる。
6. Codex の自動レビュー（`AGENTS.md` の `## Code Review Rules`）がプルリクエストに付く。マージは待たない。指摘は持ち主に届く。

## 決めたことと理由

### 定時タスクはクラウドの scheduled task

| 候補 | 判定 | 理由 |
|---|---|---|
| Claude Code のクラウドの scheduled task | 採用 | PC が要らない。VM に Node.js 22 と Chrome（`/usr/bin/google-chrome`）がある。サブスクリプションの枠で動く。最短の間隔は 1 時間 |
| systemd timer と `claude -p` | 予備 | PC が起きている必要がある。未信頼の Web を読むエージェントが、手元の認証情報と同じ権限で動く |
| GitHub Actions と claude-code-action | 予備 | 1 年有効の `CLAUDE_CODE_OAUTH_TOKEN` を公開リポジトリの secret に置くことになる |
| Claude Desktop のローカルの task、`/loop` | 不採用 | アプリかセッションが開いている間しか動かない |
| ChatGPT の scheduled task、`codex exec` | 書き手には不採用 | Web 版は結果がチャットに出る。デスクトップ版と CLI は PC の常時起動が要る |

出典は、Claude Code の文書（routines、cloud-environments、scheduled-tasks、headless、github-actions）、Anthropic のサポート記事「Use the Claude Agent SDK with your Claude plan」、OpenAI の文書（pricing、automations、third-party/github、non-interactive-mode）。2026-11-15 に読んだ。

### 書き手の権限を、リポジトリの外で絞る

クラウドの実行は、Full のネットワークで未信頼のページを読む。GitHub のプロキシは push 先のブランチを制限しないので、プロンプトだけでは main を守れない。次の形にした。

- 実行はプルリクエストを出すだけ。マージは GitHub Actions がする。
- ワークフローは `pull_request_target` で動かす。ワークフローも `tools/` も main の版が使われ、プルリクエストの側のファイルは実行されない。
- 対象は、同じリポジトリの `claude/news-*` から持ち主の名前で出たプルリクエストだけ。fork からのものでは動かない。
- 検査（`tools/news-pr-check.mjs`）は、変わるのが `news/` の直下だけで、足す `.md` が日刊のノート 1 つで、既にあるノートを変えていないことを確かめる。続けて main の `build-news.mjs` で作り直し、`.html` と README の表がプルリクエストの中身と一致することを確かめる。自由に書けるのは新しい `.md` 1 つになる。
- ノートのリンクは `https://` か `http://` で始まる URL だけ（`build-news.mjs` は `javascript:` のリンクも通すため）。章の場面へのリンクは 2 つ以上。
- 実行に付くコネクタ（Gmail・Drive・Calendar）は外す。

検査は事実の正しさを見ない。誤りは、Codex のレビューと持ち主が読んで見つける。直すのは、ふつうの作業と同じ（main へ直接）。

main に ruleset は置いていない。置くと、持ち主の手元からの直接 push もできなくなる。実行は持ち主の GitHub の権限で動くので、main への直接 push を止めているのは、手順書と auto mode である。

### GitHub Pages

Pages は main のブランチから配る設定（legacy）。GitHub の文書は、`GITHUB_TOKEN` による push は Pages のビルドを起動しないと書く。起動したという報告もある。マージの後に `POST /repos/{owner}/{repo}/pages/builds` で明示して頼む。

### 一覧を月ごとにした

一覧は 6 件で 1 場面なので、毎日 1 件では場面が増えすぎる。`news/index.html` を、新着（6 件）・月ごと（月のページへのリンク）・詳しいノート（日刊でないノート）にし、月のページ `news/YYYY-MM.html` を足した。月は、ニュースが出た月（ファイル名の日付）。README の表は、詳しいノートの表と、月の表の 2 つにした。

### 日刊の型

詳しいノートは 6 場面・15〜30 KB で、毎日は重い。日刊は 3 場面（層・中身・前提と出典）、12,000 バイトまで。行だけの印 `<!-- kind: daily -->` で見分ける。章と場面へのリンクは、章のファイルを読んで確かめた場面だけ。段階の番号は書かない（リンクにならないので、検証で確かめられない）。

### 選び方

候補を、ニュース（出来事: 新しい版、方針の変更、脆弱性の公表、障害、不正アクセス）と、記事（解説と、作ったもの・調べたものの報告）に分ける。1 巡目はニュースだけ、無ければ 2 巡目で記事を、候補の表の上から順に見て、条件（範囲、7 日以内、一次情報、2 つ以上の場面）を全部満たす最初の候補を選ぶ。どちらにも無い日は、ノートを作らない。

- ニュースを先に見るのは、持ち主の目的が、更新のニュースを層に結びつける練習だから。評価の 2 回目で、この優先が手順書から抜けていて、Lobsters で 15 点の解説が、点数の高い更新のニュースより先に選ばれた。
- 「上から順に、最初に満たした候補」にしたのは、比べる基準が複数あると、実行のたびに選ぶ記事が変わるから（評価の 1 回目）。
- 範囲は、持ち主が決めた 5 つ（Web プラットフォーム・言語・OS・ネットワーク・セキュリティ）に、教材の主題の「動画の圧縮と配信」を足した。「言語と処理系」には、データ構造とアルゴリズムの実装の話を含めた（第27章に結びつく）。

### ChatGPT の使いどころ

- Codex の GitHub の自動レビュー。Plus に含まれる。別のモデルによる査読になる。指摘は P0・P1 だけ。
- 公式の料金表（2026-11-15）は Plus $20、Business $25/人（月払い）で、$30 の枠は無い。どちらでも自動レビューは使える。

## 確かめたこと

- `build-news.mjs` の改修: ニュースの全ページ（一覧、月 5 つ、ノート 8 つ）が `verify.mjs --sizes all` で ✓。
- `news-candidates.mjs`: 3 か所から取れた（Hacker News 30 件、はてなブックマーク 30 件、Lobsters 25 件）。
- 1 件目の日刊のノート（`news/2026-11-08-dtl-nand-chip-reverse-engineering.md`、8,081 バイト）を、手順書どおりに作った。日刊の型の手本にした。
- 検査の再現: 一時置き場に main とプルリクエストのブランチを作り、ワークフローと同じ手順を走らせた。正しいプルリクエストは通る。不正なものは落ちる（既にあるノートの変更、`tools/` と `.github/` の変更、作り直していない `.html`、手で書き換えた `.html`、`javascript:` のリンク、印なし、ノート 2 つ、シンボリックリンク、削除、16,000 バイト超え、未来の日付、`news/` の下のフォルダ、章の場面へのリンクが 2 つ未満）。ワークフローの YAML そのものは、GitHub の上でしか走らせられない。

## 手順書の評価

持ち主の empirical-prompt-tuning スキルに沿って、手順書を知らないサブエージェントに実行させ、詰まった所を直した。一時置き場に、いまの作業ツリーを main にした写しを作り、GitHub の操作だけ PR.md を書くことで代えた。要件は先に決めて、変えなかった。

| 回 | シナリオ | 結果 | 要件 | ツール | 時間 | トークン |
|---|---|---|---|---|---|---|
| 1 | A ふつうの日（ノートを書き切る） | ○ | 6.5/7 | 85 回 | 22 分 | 30.4 万 |
| 1 | B その日のブランチが既にある | ○ | 3/3 | 5 回 | 2.5 分 | 6.0 万 |
| 1 | C 適う候補が無い | ○ | 3/3 | 27 回 | 9 分 | 13.1 万 |
| 2 | A | ○ | 7/7 | 59 回 | 18 分 | 24.1 万 |
| 2 | B | ○ | 3/3 | 6 回 | 2 分 | 6.1 万 |
| 2 | C | ○ | 3/3 | 14 回 | 6 分 | 10.5 万 |
| 3 | S 選ぶ段まで。同じ候補 40 件を 3 人に | 3 人とも同じ候補 | 3/3 | 51・54・64 回 | 19〜21 分 | 27.3・30.1・29.5 万 |

- 1 回目の後に直したこと: 終わり方と報告（ブランチがあるとき、候補が取れないとき）、範囲と「外すもの」（規制・制裁、AI の製品に固有の事故、意見と体験談の線）、一次情報の定義、章の読み方（段階の文はスクリプトの `const sK` にある）、取ったファイルを調べる道具と実行の境目、候補の表に投稿の日を出す。
- 2 回目の後に直したこと: ニュースを先に見る 2 巡の選び方、一次情報は中心の事実が載ったもの、検査の章の場面のリンクを 2 つ以上に、`http://` のリンクを通す。
- 3 回目は、3 人とも 1 巡目に適うニュースが無いと判定し（PyPI の更新は 7 日より前、Microsoft の障害は当事者の原因の説明が無い、Project Zero の方針の変更は場面に結びつかない）、2 巡目で同じ記事を選んだ。3 人が共通に挙げた曖昧さ（種類を話題で決めるかページの形で決めるか、「結びつく」の下限、出た日が複数あるとき、一次情報を探す深さ、会員限定の扱い）を手順書に書いた。**この最後の直しは評価していない。** スキルの収束の基準（新しい不明瞭点が 2 回続けて 0）には届いていない。費用との釣り合いで止めた。
- A の 2 回で書かれたノート（自己起動する ZIP、ボードゲームの全局面の解析）は、評価用の写しの中だけにあり、リポジトリには入れていない。どちらも検査は 1 度で通った。
- 1 回の実行の目安は、24〜30 万トークン、18〜22 分（この PC で、Fable 5.2 のサブエージェント）。選ぶ段だけで 27〜30 万トークンかかった回があり、一次情報探しの深さを手順書で限った。

## 確かめていないこと（最初の実行で見る）

- クラウドの VM で `verify.mjs` が走るか（Chrome の場所と Node.js 22）。
- プルリクエストの作成者が持ち主の名前になるか（ワークフローの `if` の条件）。
- `GITHUB_TOKEN` でのマージと、Pages のビルドの依頼が通るか。
- 1 回の実行の消費量。claude.ai/settings/usage の増分で見る。
- Codex のレビューが、外部の出典を開いて事実を照合するか。
