## 2. 方針

3 つの土台を作り、4 つの課題をその上で解く。

| 土台 | 中身 | 使う課題 |
|---|---|---|
| 層の登録簿 `assets/layers.js` | 層（§4 の 24 層の案）、層の上下の辺、全 216 場面の層。手で書く正本 | 1・3・4、2 の下の層の候補 |
| 掘り下げ `YT.drill`（`engine.js`） | 図の要素に下の層への印を付ける。押すと場面の上に板を重ね、下の層を見せる。板は入れ子にできる | 2・3 |
| 部品 `assets/parts/*.js` | 層ごとのアニメーションを、値を渡して動かせる小さな場面にしたもの。第6章の板の関数（`buildALU` など）を一般化する | 2・3 |

設計の判断（2026-11-16 に持ち主が推奨どおりと決めた。§5）:

- 掘り下げは、章へ移らず、場面の上に板を重ねる。板の上端に道筋（例: 第9章 場面3 › CPU のモード › D フリップフロップ）と、上と下をつなぐ一文を出す。閉じると元の段階に戻る。戻り先を覚えておく負担をなくすため（1 画面の方針と同じ理由）。
- 板の中身は 2 種類ある。部品があれば部品を出し、上の場面と同じ値で動かす。部品が無ければ、下の章の場面をそのまま埋め込む（`?embed=1`）。まず埋め込みで全部の境目をつなぎ、つながりの要の所から部品に置き換える。
- 下の層の説明が教材に無い所は、印を張る前に部品を足す。リンクだけでは、行き先が同じ抽象で止まる（第9章 場面3 段階2 → 第7章 場面3 段階4 がその例）。
- タグは、ノートが既に張っている章の場面へのリンクから自動で付ける（登録簿で場面を層に引く）。書き手が足すのは、中心の層の指定（`<!-- tags: … -->`。無ければ自動で決める）と、教材に無い概念（`<!-- missing: … -->`）だけにする。日刊の手順は書き足しで済む。
- グラフは層の上下を保った図にする。層を位置に固定し、ノートを層につなぐ。力学で並べるグラフは層の上下が消えるので使わない。層は位置と名前で区別し、色相で分けない（色の意味は全章で固定。選んだものだけ x）。
- 導線は本文の中のリンクにせず、上部バーのボタン、表紙の札、場面の見出しの札にする。表紙の注記の中にリンクがあっても、持ち主は「導線が無い」と指摘した。

### P2 掘り下げの仕組みと手本（大）— 済み（2026-11-17、[log/2026-11-17-p2.md](log/2026-11-17-p2.md)。計画から変えた所は log の「判断」）

手本は持ち主の挙げた第9章 場面3 段階2 にする。`syscall` から電子まで掘れるようにする。

1. `assets/engine.js`:
   - `YT.drill.mark(el, { to, part, params, bridge, steps })` を足す。`to` は下の層の場面・段階（`07-shuuhen.html#s3.4`）、`part` は部品の名前（あれば）、`bridge` はつなぎの一文（60 字まで）、`steps` は印を出す段階。
   - 印は要素の角の小さな札（x の枠と「↓」）にする。押すか Enter で開く。説明欄の下に、その段階の印の一覧を出す（縦読み版でも出す。ホバーに頼らない）。
   - 板は場面の本体（左の列と図）を覆う。上端に道筋・つなぎの一文・「章を開く ↗」・「閉じる（Esc）」を出す。入れ子は積み、Esc で 1 段ずつ戻る。段階や場面が変わると全部閉じる。開いている間は「自動で進む」を止める。開くときは印の要素の位置から広げる（`YT.zoom` と同じ動き）。
   - 中身: 部品があれば `assets/parts/<名前>.js` を読み込み、左に部品の段階の文、右に部品の図を出す。無ければ `to` の章を iframe で `?embed=1` を付けて開く。
   - 埋め込み（`?embed=1`）: 上部バー・表紙・まとめを出さず、その場面だけを出す。1画面版の倍率の下限を外す（iframe は 1216×654 より小さいことがある）。‹ › は場面の中の段階だけを動かす。「続きから」（localStorage の `ytm-last`）と URL を書き換えない。段階の変化は親へ postMessage で知らせる（同じオリジンからの通知だけを受ける）。埋め込みの中の印は親に頼み、親が板を積む。
   - `YT.parts.define(名前, { layer, home, title, steps(params), setup(g, params), onStep(ctx, i), frame(ctx, t, dt) })` を足す。部品は小さな場面で、章の場面と同じ決まりに従う（onStep が段階の見た目を全部決める。frame は dt = 0 でも描く）。
2. `assets/parts/cpu-mode.js`（新しい説明）: 第6章の YT-8 に、モードのビット M（D フリップフロップ 1 個）、入口の番地のレジスタ（LSTAR に当たる）、戻り先を置くレジスタ（rcx に当たる）を足した模式図。段階の案は次の 5 つ。
   1. M の意味（1 ならユーザー、0 ならカーネル）。
   2. 入口のレジスタは、カーネルモードでだけ書ける。
   3. `syscall`（0F 05）も、ほかの命令と同じにフェッチ・デコードされる（第6章 場面3）。実行の拍で、PC ← 入口、戻り先 ← 次の番地、M ← 0 が同じクロックで入る。
   4. メモリを読み書きするたびに、M とページの印（U/S。第9章 場面4）を論理ゲートで照らし合わせる。
   5. `sysret` で戻る（PC ← 戻り先、M ← 1）。
   - 値は第9章 場面3 と同じにする（rax = 45、fd 23）。x86 のモードは CS の下位 2 ビット（CPL）なので、図の注記に模式と書く。事実は Intel SDM（SYSCALL・SYSRET の項と、保護の章）で確かめる。
   - 部品の中の印: M → 第5章 場面2（D フリップフロップ）、照らし合わせのゲート → 第4章、PC と戻り先 → 第5章 場面3（レジスタ）。
3. 第9章の印: 場面3 の `syscall` の行と「CPU がモードを切り替える」の線 → cpu-mode。`entry_SYSCALL_64` → 第7章 場面3 段階4（割り込みも同じく決まった入口へ飛ぶ。違いは合図の出どころと戻り先の置き場）。NIC → DMA の帯 → 第7章 場面4。場面1 段階2・3 も cpu-mode へ。手本として、第5章 場面2 → 第4章 → 第3章 → 第2章 → 第1章 の印を 1 本ずつ通す（行き先は P4 の棚卸しと同じ基準で選ぶ）。

5. `docs/authoring.md` に「掘り下げ」の節を足す（印の付け方、つなぎの一文、部品の書き方、検証）。

### P6 ニュースの台本（大）

ノートごとに「何が起きたか」を動かす。日刊は自動でマージするので、ノートに JS を書かせない。

1. 汎用の部品を作る: やりとりの列（seq: 送り手と受け手の間の矢印）、メモリの区画（mem: 確保・解放・指す）、層の積み重ね（stack）、箱と線（boxes: プロセス・サービス）、木（tree: 証明書の連鎖・DOM）、時間の軸（timeline）。
2. ノートの中の ```` ```anim ```` ブロック（部品の名前と、段階ごとの文と状態）を `build-news.mjs` が読み、検査して（形、段階 6 まで、本文 160 字まで）場面にする。描くのは手で書いた部品で、ノートの文字は文字としてだけ扱う（HTML として挿し込まない）。
3. 詳しいノート（持ち主が予想を書くもの）は、部品で足りなければ手書きの JS（`news/anim/<名前>.js`）も使える。日刊の検査は news/ の直下しか許さないので、今のままでこれを通さない。
4. 検収: 既存の 2 件（Linux の TCP の解放後の使用・eMudhra）に台本を書き、1画面に収まり `verify.mjs` が ✓。日刊では 1 週間試してから、手順書で必須にするかを決める。
